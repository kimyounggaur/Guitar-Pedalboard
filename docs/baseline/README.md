# 오디오 렌더 프로브 기준선

실제 이펙트 클래스와 워클릿을 `OfflineAudioContext` 로 렌더해 소리를 숫자로 잰 값이다. 음질을 건드리는 Step 은 이 값이 어떻게 달라졌는지로 판정한다(설계서 6.2절).

| 파일 | 내용 |
|---|---|
| `audio-probe.json` | 기준선. 프로브 25개 × 샘플레이트 2개(44.1·48 kHz), 측정값 1,714개 |
| `tolerances.json` | 항목별 허용 오차. 넓히거나 `ignore` 를 늘리려면 사람 승인이 필요하다(설계서 6.4절) |
| `e2e.json`, `screenshots/` | 브라우저 시나리오(E-04·E-06) 기준선. 설명은 `README-e2e.md` |

## 쓰는 법

```bash
npm run probe                          # 전부 돌려 기준선과 비교 (약 5분, CPU 2개 기준. P-05 가 샘플레이트당 80~95초)
npm run probe -- --only P-04,P-13      # 일부만
npm run probe -- --rates 48000         # 샘플레이트 지정
npm run probe -- --verbose             # 모든 측정값 출력
npm run probe -- --update              # 기준선 갱신 (의도한 변화일 때만)
```

- 기준선을 갱신하는 커밋의 메시지는 `baseline: {Step ID} {이유}` 로 쓴다. 이유 없이 갱신하지 않는다.
- `tolerances.json` 의 `criteria` 는 기준선과 상관없는 **절대 수용 기준**(하한 `atLeast`·상한 `atMost`)이다. 매번 비교할 때 함께 검사하고, 어기는 값은 `--update` 로도 기준선이 되지 못한다. 지금 걸린 것(Step 별): S1.1 P-01 `differenceDb ≥ 30`·P-02 `outputDropDb ≥ 25`, S1.3 P-06 `auto.*` 5개, S1.4a P-03 `peakWithLimiterDb`·`defaultCabOffPeakDb ≤ −0.9`, S1.4b P-04 `maxAbsDiffDb ≤ 1.5`, S1.4c P-05 음량 정렬·리미터 감소량·'음량 맞추기' 오차 10여 개, S1.5 P-07 `hits ≥ 4`·`maxMutedSeconds ≤ 1.5`·`minMutedSeconds ≥ 1.0`·`falseCuts ≤ 0`·`silentFailures ≤ 0`·`disabledModeCuts ≤ 0`·`disabledModeSoundDb ≥ −30` 와 P-17 `ratio.monitorOverheadOverPedals ≤ 0.05`, S2.1 P-18 3개(`unchangedUnexpected ≤ 0`·`loadNullDb ≤ −90`·`loadUntouchedOffPedals ≤ 0`), S2.2 P-20 3개(`nullDb.* ≤ −90`·`convertedDecayError ≤ 0`·`maxFactoryDecay ≤ 6`)·P-21 `displayedSilenceDb` −0.5 ~ 0·P-24 6개(잡음 감소 ≤ −30 dB 둘, 워클릿 정확 일치 둘, 레벨 차 ≤ 0.01 dB, 첫 음 손실 ≥ −1 dB), S2.4 P-19 7개(`nullDb.* ≤ −80` — 이것이 설계서의 기준이고, 판정 규칙은 −90 dB 로 더 엄격하다 — 와 `activeMismatch ≤ 0`·`presetMissing ≤ 0`·`visit1.legacy ≤ 0`·`visit2.v2 ≥ 6`·`boardsChecked ≥ 6`·`presetsChecked ≥ 3`), S3.2 P-25 `maxClickRatioDb ≤ 6`. 전체 목록과 이유는 `tolerances.json` 의 `criteria` 에 있다. Step 이 수용 기준을 맞출 때마다 여기에 더한다.
- `npm test` 가 `test:probe` 로 이 비교를 함께 돈다. 시험 제한 시간만 900초로 늘려 두었다(`scripts/run-all-tests.mjs`).
- Chrome 이 없으면 로컬에서는 건너뛰고(종료 코드 0, 경고 출력) CI(`CI=true`)에서는 실패한다. `CHROME_PATH` 로 Chrome 을 지정할 수 있다.
- 기준선을 만든 환경: Chrome/153.0.8010.12, Linux x64, Node v22. 브라우저 버전이 다르면 비교 때 경고가 나온다. 값이 흔들리면 Chrome 버전을 고정하고 별도 PR 로 기준선을 갱신한다(설계서 6.4절).

## 재현성

같은 코드로 두 번 돌린 결과를 견주었다(S0.3 시점, 측정값 490개). 그 가운데 P-17 의 시간 계열 24개만 달랐고 나머지는 비트 단위로 같았다. S1.5 의 P-07 은 고정 신호와 결정적인 판정이라 되풀이해도 같다(판정 조기 반환을 넣기 전후로 차단 시각·의심 횟수·차단 주파수가 같았다). P-17 은 벽시계 시간을 재므로 기계에 따라 달라진다. `time.*` 은 비교하지 않고, `cpuShare.*` 는 기준값의 4배를 넘는 폭증만, `ratio.*` 는 ±0.3 으로 느슨하게 본다. 잔차(널) 시험 두 가지(P-05 `bypassNullDb`, P-20 `nullDb.*`)는 수치 잡음 바닥이라 상한(−90 dB)만 본다.

### P-25 (S3.2) 읽는 법

- P-25: Cab 의 IR 이 바뀔 때 생기는 클릭을 잰다. 신호가 일정한 사인파(220 Hz·660 Hz)라 소리가 부드럽게 바뀌면 출력의 1차 차분(이웃 표본 사이 변화)의 최대값이 동작 앞뒤의 고른 구간과 같다. 동작 구간의 최대값이 앞·뒤 고른 구간 중 큰 쪽보다 몇 dB 큰지가 `clickRatioDb.주파수.동작` 이고 그중 가장 큰 값이 `maxClickRatioDb` 다(수용 기준 +6 dB 이하). 동작 네 가지: `mic`(마이크 위치 한 번 55→85), `model`(V30→Blue), `micDrag`(마이크 위치를 20 ms 마다 1씩 31번), `distanceDrag`(거리). 신호의 크기에 비례하므로 큰 점프가 크게 나오고, 같은 코드면 두 번 돌려도 같은 값이다.
- 이 프로브는 이펙트가 거는 타이머를 렌더 시각으로 재야 하므로 `renderChain` 이 `createContextTimers` 를 이펙트에 넘긴다. 창 타이머를 쓰는 이펙트(리버브)는 렌더 도중에 바뀌지 않는다.

### 이 표에서 읽을 점

- 보고서에 있던 큰 결함 가운데 P-01·P-02·P-04·P-08·P-09·P-11·P-15·P-21 은 이미 고쳐져 있다. 이 항목들의 Step 은 "새로 고치기"가 아니라 "고쳐진 상태가 지켜지는지 확인하기"로 진행한다.
- 아직 열려 있는 방향: P-12(Phaser 빗살), P-13(Distortion 낮은 노브), P-16(Drive·Crunch·Fuzz 지연), P-17(꺼진 Phaser 비용). P-20(저장된 Decay 7.5초)은 S2.2 에서 해결했고, P-19(v1 → v2 동일성)는 S2.4 에서 처음 재어 통과했다.
- 코드 지도(`docs/refactoring/code-map.md`)가 "구현됨"으로 분류한 Step 중 위 ✖ 에 걸리는 것은 Step 을 시작할 때 다시 대조한다.

## 측정 방식 메모

- 체인 구성: 소스 → 입력 레벨 미터(`monitoring`) → (장치 모드면 `InputStage`: 채널 선택 `inputChannelMode`·자동 판정. 2채널 입력은 렌더 도중 50 ms 마다 입력 샘플에서 직접 채널 레벨을 재서 판정한다) → 입력 게인 → 이펙트(페달 순서) → `OutputStage`(프리셋 보정 → 마스터 0.9 → 출력 가드 → 리미터) → 출력 레벨 미터 → 출력. 실제 앱의 `AudioEngine` 과 같은 클래스를 쓴다. 레벨 미터·가드는 `monitoring: false` 로 뺄 수 있고(S1.5 이전 모양), 가드는 기본 `guardMode: 'off'` 라 소리를 건드리지 않는다. P-07·P-17 만 `'device'` 로 하울링 판정을 켠다(L-46). 리미터는 소리를 룩어헤드 1 ms 늦추는데, 입력과 출력을 같은 시각으로 맞춰 비교하는 측정(전달함수 P-11·P-12, 클릭 창 P-23, RMS 창)이 어긋나지 않도록 렌더는 이 고정 지연을 걷어 낸다(`alignOutput`, 기본 켬, REFACTOR_LOG L-30). 처리 지연을 재는 P-16 만 걷어 내지 않아 리미터의 1 ms 까지 읽는다.
- 렌더 앞에 0.5초 무음을 붙인다(`BaseEffect` 의 파라미터 스무딩 τ≈12 ms 가 안정되도록). 모든 측정은 이 구간 뒤에서 한다.
- 꺼진 페달은 신호를 그대로 통과시키므로 P-05 는 체인에서 뺀 채 렌더해 시간을 줄이고, 첫 프리셋을 15개 전체로 한 번 더 렌더해 같음을 확인한다(`bypassTransparent`).
- 신호는 모두 고정 시드로 만든다(`src/audio/testing/signals.ts`). WAV 는 `node scripts/make-fixture-wavs.mjs` 가 `e2e/fixtures/` 에 만든다(S0.4 가짜 마이크용, git 에는 넣지 않음). S2.5 가 입력 레벨 경고 시험(E-09)용 신호 4종을 더했다: `lvl-small`(REF-PC 의 모든 타건 피크 −40 dBFS)·`lvl-hot`(0 dBFS)·`lvl-silent`(10초 무음)·`lvl-stop`(한 번 치고 멈춤, 14초). 부록 A 의 기준 신호가 아니고 오디오 프로브(P-xx)는 쓰지 않는다(REFACTOR_LOG L-126).
- 프로브 페이지(`probe.html`)는 `vite build --mode test` 에서만 빌드되고 `dist-probe/`(gitignore)에 나온다. 일반 빌드와 GitHub Pages 배포에는 들어가지 않는다.


### P-05 (S1.4c 이후) 읽는 법

- 프리셋마다 REF-PC 를 두 번 렌더한다: ① 보정·리미터 없이(`rawDb.*`·`rawPeakDb.*` — `npm run trims` 가 trim 을 계산하는 입력), ② 앱이 내보내는 소리 그대로(팩토리 trim + 리미터: `preset.*`·`peakDb.*`).
- `deviationDb.*` 는 ② 의 평균이 프리셋의 **도달 가능한 목표**(`achievableTargetDb.*`: 표준 −20 dBFS 또는 D6 예외 목표, 단 피크가 0 dBFS 를 넘지 않는 곳까지)에서 벗어난 양이다(판정 ±2). 표준 목표에서의 거리는 `offTargetDb.*`·`maxAbsOffTargetDb` 로 따로 남긴다(≤ 3).
- `limiterReductionDb.*`·`maxLimiterReductionDb` 는 보정한 피크가 리미터 천장(−1 dBFS)을 넘는 양이다(GS-7, ≤ 1 dB). `quickMeasureErrorDb.*`·`quick.*` 는 '음량 맞추기' 버튼(4초 렌더)이 8초 렌더와 얼마나 다른지 본다.
- 팩토리 trim 을 다시 계산하려면 `npm run trims`(기준값은 `src/audio/offline/loudnessSpec.ts`). trim 이 바뀌면 이 기준선도 같은 Step 에서 갱신한다.
- 측정만 하고 기준선과 비교하지 않으려면 `node scripts/audio-render-probe.mjs --only P-05 --no-compare` (`--out 파일` 로 결과 저장).

### P-20·P-24 (S2.2) 읽는 법

- P-20: 옛 저장값(공장 프리셋 6.2·7.5초, 옛 최댓값 10초)으로 렌더한 Reverb 출력과, 앱이 불러올 때 쓰는 함수(`clampPedalsToSchema`)로 맞춘 6.0 초의 출력을 견준다. 엔진은 처음부터 6 초에서 임펄스를 잘라 써서 널은 −200 dB(완전히 같음)이고, 변환이 정확한지는 `convertedDecayError`(바뀐 값과 6.0 의 최대 차이, 초)가, 공장 데이터가 6 초를 넘지 않는지는 `maxFactoryDecay` 가 맡는다.
- P-24: Fuzz 의 Gate 를 잰다. **체인 전체의 파형 널은 쓰지 않는다** — 같은 체인을 두 번 렌더하면 입력이 1 ppm 만 달라도 약 −80 dB 의 수치 잡음이 남는다(REFACTOR_LOG L-90). 대신 게이트 워클릿만 따로 돌려 입력과 다른 샘플 수(`gate0.workletDiffSamples`·`open.workletDiffSamples`)와 체인 출력 레벨 차(`open.levelDiffDb`)를 본다. `noise.*` 는 앱 기본 Mix(90%)라 게이트를 지나지 않는 원음이 섞여 있고, `noiseMix100.*` 은 Mix 100% 다. `onset.lossDb` 는 쉬었다 시작하는 음(110 Hz)의 처음 10 ms 가 Gate 50 때문에 줄어든 양이다.
- 기준선이 달라진 프로브는 P-03(최악 조합의 리미터 앞 피크 +0.7 / +0.6 dB — 44.1 / 48 kHz)·P-05(Fuzz 프리셋 5개의 raw·trim)·P-20(지표 재정의)·P-24(신규)·P-25(신규) 다섯이다. 나머지는 허용 오차 안이다.

### P-19 (S2.4) 읽는 법

- 프로브 빌드(`--mode test`)에만 v1 픽스처 6개(`e2e/fixtures/storage-v1`)가 `import.meta.glob` 으로 들어간다. 배포 번들에는 들어가지 않는다. 픽스처마다 시험용 저장소(Map)에 넣고 앱이 열 때의 절차 `runBootstrap` 을 두 번 돈다. 첫 방문은 v1 에서 v2 로 옮기고(`visit1.converted`·`visit1.fresh`·`visit1.legacy` 는 그 결과의 개수. v1 값이 없는 픽스처 01 은 `fresh`), 둘째 방문은 v2 키에서 읽는다(`visit2.v2`).
- 소리는 둘째 방문에서 읽은 **작업 보드와 사용자 프리셋**으로 낸다. 정답은 같은 v1 원문에서 옛 앱의 규칙(켜짐 = `enabled` 이고 `bypassed` 가 아님, 값은 저장된 그대로, 순서는 저장된 순서)으로 따로 만든 체인이라 변환 코드와 같이 틀릴 수 없다. 둘을 REF-PC 1초로 렌더해 출력 차를 출력 대비 dB 로 적는다(`nullDb.board.NN`·`nullDb.preset.NN.K`, −200 은 완전히 같음).
- 시간을 줄이려고 꺼진 페달은 체인에서 뺀다(꺼진 페달은 신호를 그대로 통과시킨다). 어느 페달이 켜져 있는지는 `activeMismatch`(켜진 페달 목록이 옛 규칙과 다른 보드·프리셋의 수)가 따로 견준다. `presetMissing` 은 둘째 방문에서 사라진 사용자 프리셋의 수다(둘 다 0). `activeCount.NN` 은 보드의 켜진 페달 수(5/2/5/5/6/5)이고, 이 값이 바뀌면 픽스처나 규칙이 바뀐 것이다.
- 꺼진 페달의 Mix 복원(M2)은 꺼져 있는 동안 소리에 영향이 없으므로 여기서 보이지 않는다. 그것은 P-18 의 `loadNullDb` 가 본다.
- 걸린 기준: `criteria` 7개(`nullDb.* ≤ −80` 이 설계서의 기준)와 `rules` 의 `nullDb.* ≤ −90`. 변환이 틀리면 소리가 바뀌기 전에 `visit1.legacy` 가 0 보다 커진다 — 틀린 변환은 v2 로 굳히지 않고 옛 방식으로 열기 때문이다(REFACTOR_LOG L-107).
- 이 프로브가 재지 않는 것: 실제 사용자의 데이터(고정된 픽스처 6개뿐), S2.2 에서 달라진 Fuzz 의 소리(변환은 값을 바꾸지 않는다 — L-116), 브라우저의 실제 `localStorage`(시험용 Map 이다).
