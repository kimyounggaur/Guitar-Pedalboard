# 브라우저 시나리오(E2E) 기준선

실제 Chrome 에서 앱을 열어 화면 배치·도달성·시작 동작을 재는 시험이다(설계서 6.3절). 오디오 렌더 프로브(`README.md`)가 '소리'를 재듯, 이쪽은 '화면에서 손이 닿는지'를 잰다.

| 파일 | 내용 |
|---|---|
| `e2e.json` | E-04(S1.6 부터)와 E-06(S1.8 부터) 시험이 남긴 기준 측정값. 두 시험 모두 정식 단언이고, 화면 프로필 × 조건별로 한 덩어리 |
| `screenshots/` | 지금 상태를 눈으로 보기 위한 대표 스크린샷 6장(휴대폰 390×844 도크 접힘·펼침, 노트북 1280×800·1440×900 패널 펼침, 1024×768 서랍 열림, 1280×800 기타 연결 뒤). 비교에는 쓰지 않는다 |

## 쓰는 법

```bash
npm run build                         # 시험은 빌드 결과(dist/)를 vite preview 로 서비스한다
npm run e2e                           # 빌드까지 알아서 한다. 전체 266개, 약 12분
E2E_SKIP_BUILD=1 npm run e2e          # dist/ 가 이미 있을 때(CI 는 앞 단계에서 빌드해 이렇게 돌린다)
npm run e2e -- --grep "E-23"          # 일부만
E2E_UPDATE_BASELINE=1 npm run e2e     # 기준선(e2e.json)과 대표 스크린샷 갱신 (의도한 변화일 때만)
# 측정값을 남기는 시험만 돌려 갱신할 수도 있다(E-04 + E-06, 약 1분. 병합이라 나머지 값은 그대로다)
E2E_UPDATE_BASELINE=1 E2E_SKIP_BUILD=1 npx playwright test e2e/tests/e04-phone-reachability.spec.ts e2e/tests/e06-desktop-layout.spec.ts
```

| 환경 변수 | 뜻 |
|---|---|
| `E2E_SKIP_BUILD=1` | `npm run build` 를 건너뛰고 있는 `dist/` 를 쓴다 |
| `E2E_UPDATE_BASELINE=1` | E-04·E-06 이 잰 값을 `docs/baseline/e2e.json` 에 병합하고 대표 스크린샷을 `screenshots/` 로 복사한다(조건별로 값 전체를 교체한다) |
| `E2E_CHROME_PATH` | 시험에 쓸 Chrome 실행 파일. 없으면 Playwright 가 받은 Chromium(`npx playwright install chromium`)을 쓴다. `CHROME_PATH`(반응형 시험·프로브가 쓰는 변수)와는 일부러 분리했다 |

- 기준선을 갱신하는 커밋의 메시지는 `baseline: {Step ID} {이유}` 로 쓴다. 이유 없이 갱신하지 않는다.
- 시험 결과(`test-results/`)와 보고서(`playwright-report/`)는 git 에 넣지 않는다. CI 에서 실패하면 두 폴더를 `e2e-report` 이름으로 올린다(7일 보관).
- 가짜 마이크용 WAV 는 `node scripts/make-fixture-wavs.mjs` 가 `e2e/fixtures/*.wav` 로 만든다(git 제외). `e2e/global-setup.ts` 가 `--missing` 으로 **빠진 것만** 만든다(있는 파일은 건드리지 않는다. 신호가 늘어난 뒤 옛 WAV 만 가진 환경이 새 신호 없이 시험을 시작하지 않는다 — S2.5 에서 `ref-pc.wav` 하나만 확인하던 것을 고쳤다). 입력 레벨 경고용 신호 4종(`lvl-small`·`lvl-hot`·`lvl-silent`·`lvl-stop`)은 부록 A 에 없는 신호라 `README.md` 의 신호 표와 REFACTOR_LOG L-126 에 적었다.

## 하네스 구성

- 설정: `playwright.config.ts` — 작업자 1개, 데스크톱 Chrome 프로필, 마이크 권한 허용, `vite preview` 를 웹 서버로 띄움(`http://127.0.0.1:4173/Guitar-Pedalboard/`).
- 가짜 마이크: Chrome 인자 `--use-fake-ui-for-media-stream`, `--use-fake-device-for-media-stream`, `--use-file-for-fake-audio-capture=<WAV>`. WAV 는 브라우저를 띄울 때만 정할 수 있어서 `launchWithMic(wav)` 픽스처가 WAV 마다 브라우저를 새로 띄운다.
- 도우미(`e2e/helpers/`):
  - `geometry.ts` — 도달성(`reachable`: 뷰포트 가운데로 스크롤해 가운데 히트 테스트, `reachableAboveDock`: 휴대폰 도크 위 빈 영역 기준), 노출 비율, 글자 겹침, 도크 위에 온전히 보이는 노브 수(`visibleKnobs`).
  - `switches.ts` — 스위치 15개 측정(`measureSwitches`: 데스크톱, `measureSwitchesAboveDock`: 휴대폰 도크 기준).
  - `app.ts` — 앱 조작(`connectGuitar`, 도크 탭 고르기 `selectMobileTab`, 도크 펼침·접힘 `setMobileDock`: `--dock-h` 가 실제 높이를 따라올 때까지 기다림).
  - `storage.ts` — 저장소 시험 도우미(S2.4): 저장 키 이름, 페달 15개 표(`PEDALS`)와 기본으로 켜진 다섯, `seedStorage`(픽스처를 `localStorage` 에 한 번만 넣기), 저장된 v2 보드·프리셋 읽기, `toastOf`, 옛 저장본 픽스처 읽기(`loadV1Fixture`).
  - `dist-server.ts` — `dist/` 를 서비스하는 작은 서버(S2.4). 시험 도중에 `sw.js` 의 바이트를 바꿔 내려 줘서 새 버전 배포를 흉내 낸다(실제 서비스 워커가 필요한 새 버전 알림 시험용). `node:http` 선언은 `types/node-shim.d.ts` 에 있다.
  - `level-notice.ts` — 입력 레벨 경고 관찰(S2.5, E-09). 앱 코드보다 먼저(`page.goto` 전에) 심는다. 입력 쪽 `level-meter` 의 보고를 엿보아 **오디오 시계**(보고의 frame / sampleRate — 판정이 쓰는 시간과 같은 기준)를 알고, 화면의 경고 요소(`data-level-warning`)가 바뀔 때마다 그때의 오디오 시각과 함께 기록한다. `waitForAudioClock(page, 초)` 는 오디오 시계가 그 시각에 이를 때까지 기다린다(벽시계에는 마이크를 여는 시간·Playwright 왕복이 섞여 4.12 표의 초 단위 기준을 잴 수 없다). S2.5 이전 앱의 입력 경고(속성 없음)는 'legacy' 로 기록해 옛 코드에서 같은 시험을 돌려 볼 수 있다.
  - `file-media.ts` — 음원 파일 모드 관찰(S2.6, E-10). 앱 코드보다 먼저(`page.goto` 전에 `trackFileMedia`) 심는다. `new Audio()` 로 만들어지는 `<audio>` 요소를 모두 모아 재생 위치·멈춤·끝남·`loop`·`src` 속성 유무를 읽게 하고(`readFileMedia`·`currentFileElement`), 음원 파일(오디오 Blob)의 Object URL 만들기·해제를 기록한다(워클릿 스크립트용 Blob 은 센 것이 아니다). `sampleFilePosition`·`countRewinds` 는 재생 위치를 일정 간격으로 읽어 처음으로 되감긴 횟수를 센다(반복 확인). 화면 쪽은 '음원 파일 플레이어' 묶음 안의 버튼 선택자(`fileButton` — 녹음 패널에도 '정지' 가 있어 묶음 안으로 좁힌다)와 열기·닫기·막대·반복 스위치 선택자, 사용자가 하는 그대로 한국어 버튼 → 파일 선택 창(`filechooser`)으로 여는 `openFileThroughButton`, 단축키를 시험하기 전에 포커스를 비우는 `releaseFocus` 가 있다.
  - `preset-io.ts` — 프리셋 내보내기·가져오기 관찰(S2.7, E-11). 프리셋 알림 문구(`presetMessage`)·전체/라이브러리별 개수(`totalPresetCount`, `libraryCount`)·내 프리셋 저장(`saveUserPreset`)·내려받기 가로채 읽기(`exportToDownload`)·**파일 선택 창으로 가져오기**(`importThroughChooser` — `filechooser` 이벤트를 기다려 파일을 건넨다)·붙여넣기 대화상자(`pasteImport`)·충돌 대화상자(`conflictDialog`). 가져올 파일은 `test-results/e11-import-files/` 에 ASCII 이름으로 쓴다(`writeImportFile`) — 이 환경의 Chromium 은 한글·`·` 가 든 경로의 파일을 선택 창에 건네도 `change` 가 오지 않는다(L-147).
  - `touch.ts` — CDP `Input.dispatchTouchEvent` 로 손가락 드래그를 보내고 스크롤이 가라앉기를 기다린다(Playwright 의 `touchscreen` 은 탭뿐이다).
  - `mocks.ts` — 저장소 차단·가득 참, Web MIDI, 문서 숨김 흉내, `getUserMedia` 오류 7종, `AudioContext` 추적, 출력 가드 관찰.
  - `teardown.ts`(정지 정리 관찰, E-01), `screens.ts`(화면 프로필 11종), `fixtures.ts`·`env.ts`(브라우저 띄우기·환경 상수), `record.ts`(측정값 기록).
- 도우미 자체의 시험은 `e00-harness.spec.ts`(11개). 가려진 요소를 정말 '도달 불가'로 가려내는지(도크 가장자리 요소 포함), 겹친 글자를 세는지, 모의가 이름 그대로 동작하는지를 확인한다.
- 저장소·오류 시험은 `e05-storage.spec.ts`(E-05, 7개, S1.7) — 아래 'E-05' 절.
- 결함 회귀 시험은 `f-regressions.spec.ts`(11개) — F-1(숫자 입력 겹침)·F-3(세로 터치 스크롤)·F-4(노브 가운데 드래그)가 되살아나면 실패한다. 고치기 전 CSS 로 되돌려 돌리면 실패함을 확인했다.
- 데스크톱 배치 시험은 `e06-desktop-layout.spec.ts`(E-06, 31개, S1.8) — 아래 'E-04 와 E-06' 절.
- 저장된 옛 데이터를 불러올 때의 화면 시험은 `s2-1-off-pedal-mix.spec.ts`(3개, S2.1) — 픽스처 04(꺼진 Delay·Reverb·Chorus 의 Mix 0%)를 열면 기본 Mix 로 보이고, 같은 사용자 프리셋을 불러와도 같으며, 공장 프리셋에서 꺼진 페달의 Mix 가 0% 인 것이 없다. 소리 자체는 오디오 프로브 P-18 이 본다. 기준선(`e2e.json`)에는 기록하지 않는 단언 시험이다.
- 조절기 이름·범위·기능 시험은 `s2-2-param-schema.spec.ts`(8개, S2.2) — 화면의 모든 슬라이더(15개 카드)를 읽어 `src/audio/params` 스키마의 이름·범위·간격·표시와 견주고(처음 화면, 양 끝값), Fuzz Gate('출력 감쇠' 는 없음, 0 = 끔, 1~100 = 문턱 dB)·EQ Level 0~200(공장 Solo Boost 108)·Delay Sync(D.Time 막힘·동기된 값·Slapback 예외)·BPM·Reverb Decay 6초(7.5초 저장본과 공장 프리셋 둘)·프리셋 패널(막대·Store 탭 없음)을 단언한다. 그래픽 EQ 와 Reverb Tone 의 `aria-valuetext` 는 화면 글자와 일부러 다르게 풀어 쓴 문구라 숫자·단위가 같은지만 본다. 기준선(`e2e.json`)에는 기록하지 않는 단언 시험이다.
- 연결 오류 안내 시험은 `e07-connect-errors.spec.ts`(E-07, 17개, S2.3) — `getUserMedia` 를 오류 7종으로 거부시키면 설계서 4.13 의 한국어 문구(시험 파일에 글자 그대로 적었다)가 `role="alert"` 로 **화면 안에 전체가** 보이고 영어 원문·오류 이름이 없음(7개), 워클릿 로드 실패(`addModule` 거부)·비보안 출처(`isSecureContext` false)가 장치 시작 실패와 다른 문구임, 골라 둔 장치가 없을 때(OverconstrainedError·NotFoundError) 기본 장치로 다시 연결되고 경고 토스트가 뜨며 선택이 기본 장치로 돌아오고 다음 연결에서 되풀이되지 않음, 기본 장치로도 실패하면 두 번만 시도하고 컨텍스트가 남지 않음, NotReadableError 는 다시 시도하지 않음, 휴대폰 3종(390×844·360×640·412×915)의 입력 탭에서 안내 전체가 화면 안에 보임을 단언한다. 기준선(`e2e.json`)에는 기록하지 않는 단언 시험이다.
- 스위치 통합·저장 형식 시험은 `e08-active-led.spec.ts`(E-08, 12개, S2.4) — 발스위치는 카드마다 하나이고 첫 화면의 켜진 LED 가 기본 5개(Noise Gate·Compressor·Drive·EQ·Cab)임, 기타를 연결하면 미터의 이펙트 수 '5개' = LED 수이고 스위치·단축키·프리셋으로 바꿔도 LED·미터·저장된 상태가 함께 바뀜(2개). 옛 저장본 픽스처 6종(`e2e/fixtures/storage-v1`)마다 LED 수 = 저장돼 있던 켜진 페달 수(5/2/5/5/6/5), v1 키 원문은 변환 뒤·스위치·노브·새로고침 뒤에도 그대로(깨진 값을 담은 03 은 원래 키가 보관 사본으로 옮겨지고 원문이 사본에 남음), 새로고침해도 v2 에서 읽음(6개). 옛 사용자 프리셋(02)의 `enabled`·`bypassed` 조합이 켜짐 하나로 불러와지고 프리셋을 더 가져와도 v1 프리셋 키는 그대로(1개). `schema` 3(더 새로운 앱)은 옛 방식 모드로 v1 에서 읽고 v1 키에 쓰며 v2 키를 만들지 않음(2개). 도우미의 페달 표가 화면과 같음(1개). 소리가 같은지는 P-19 가 잰다.
- 두 탭 경고 시험은 `s2-4-cross-tab.spec.ts`(5개, S2.4) — 다른 탭이 v1 키 둘 중 어느 쪽에 값을 쓰든 경고 알림 한 장(문구는 설계서 4.7 그대로, 닫을 때까지 남음, 2개), 이 앱끼리의 v2 키 쓰기(스위치·노브)·v1 키 삭제·저장소 비우기에는 없음, 닫은 뒤 5분 안에는 다시 안 뜸, 옛 방식 모드로 연 탭은 알리지 않음. 옛 탭은 같은 키에 값을 쓰는 것으로 흉내 낸다.

## 고친 결함과 후보 (설계서에 없음)

**F-1 — 그래픽 EQ 숫자 입력이 투명한 전체 세로 막대가 되어 주 화면의 마우스·터치를 가로챘다. (S1.6 에서 고침, 커밋 `ce5b95f`)**

- 원인: `src/styles/pedals.css` 의 `.vertical-fader input { position: absolute; z-index: 3; inset: 0; … opacity: 0 }` 가 페이더의 슬라이더뿐 아니라 숫자 입력 `input.knob-number-input` 까지 잡았고, 바깥 `.vertical-fader` 에 `position` 이 없어 `inset: 0` 이 화면 전체 열을 기준으로 퍼졌다. 15개 페달 스위치가 전부 투명 입력 15개에 가려졌다(실제 `page.mouse.click` 도 가로채임, 키보드 Enter 는 동작).
- 들어온 시점: 설계서 기준 커밋 `4ac9cf7` 이후(커밋 `39bac60`, PR #1 병합). 배포된 앱에도 있을 가능성이 높다. **고침은 `phase/1` 브랜치에만 있고 배포하지 않았다.**
- 고침: 규칙을 `.vertical-fader-rail input` 으로 좁히고, 숫자 입력은 자기 칸 안(`.vertical-fader { position: relative }`)에만 머물며 `pointer-events: none` 으로 두었다. 키보드·스크린리더 포커스가 오면 드러나서(opacity 1) 쓸 수 있다. **터치 사용자는 그래픽 EQ 숫자 입력을 여전히 볼 수도 쓸 수도 없다**(접근성 후속 과제).
- 하네스: 한동안 `connectGuitar` 가 클릭 대신 포커스 + Enter 를 썼다. S1.6 에서 걷고 실제 `click()` 으로 돌아왔다.

**F-3 — 모바일 `.pedal-board { touch-action: pan-x }` 가 페달 카드 위에서 시작한 세로 터치 스크롤을 막았다. (S1.6 에서 고침, 커밋 `379a585`)**

- 390 px 폭에서 카드 높이가 약 1,100 px 이라 손가락이 거의 항상 카드 위에서 시작하는데, 세로로 끌어도 문서가 움직이지 않았다(0 px). `touch-action: manipulation` 으로 바꾸니 285 px 움직인다(가로 스와이프는 그대로). 아래쪽 스위치로 내려가는 길이 막혀 있던 별개의 원인이다. 배포된 앱에도 있을 가능성이 높다.

**F-4 — 노브의 장식 층이 투명한 range 입력의 가운데를 덮어, 노브 한가운데를 마우스로 끌어도 값이 안 바뀌었다. (S1.8 에서 고침, 커밋 `3b1b655`)**

- 원인: 노브 껍데기의 링·바늘·가운데 캡(Noise Gate 의 `i`, 공용·Compressor·Drive·Reverb 껍데기의 `::before`·`::after`)이 `pointer-events` 제한 없이 입력 위에 겹쳐 있어, 가운데를 누르면 입력 대신 장식이 포인터를 받았다. 1920×1080 에서 range 입력 101개 중 **13~14개**의 가운데가 그랬다(S1.8 직전 코드 `0f56ef7` 에서 회귀 시험이 14곳을 잡았고, 카드 배치를 바꾼 뒤의 스캔은 13곳이었다 — S1.6 의 추정은 착시가 아니었다). 고치기 전에는 그 노브의 가운데를 끌어도 값이 그대로였고, 가운데가 비어 있던 노브(대조군 10개)는 바뀌었다. 앱 기준 커밋 `2a5ab81` 에서도 같은 CSS 라 오래된 결함이고 배포된 앱에도 있을 가능성이 높다. **고침은 `phase/1` 브랜치에만 있고 배포하지 않았다.**
- 고침: `pedals.css` 끝에 장식 층 네 곳(`::before`·`::after`·`i`·`i::after`)에 `pointer-events: none`(대상: 클래스 이름에 `knob-shell` 이 든 껍데기 전부와 `.knob-control-shell`). 노브를 조작하는 **방식** 자체(S4.4 범위)는 바꾸지 않았다. 따로 떼어 cherry-pick 할 수 있다.
- 회귀 시험: `f-regressions.spec.ts` 5개(모든 노브 가운데의 히트 테스트 + 장식 층 종류별 마우스 끌기 4개). `0f56ef7`(고치기 전) 코드에서 돌리면 5개 모두 실패한다(히트 테스트가 14곳을 잡고, 끌기 4개는 값이 그대로).
- **터치로는 확인하지 못했다.** 손가락으로 가운데를 끌었을 때 같은지 사람이 본다.

## 아직 사람이 확인해야 하는 것

- 위 F-1·F-3 이 실제 배포 사이트(GitHub Pages)에서도 일어나는지, 그리고 고친 빌드에서 사라지는지 — 실제 휴대폰에서 페달 카드 위로 손가락을 끌어 스크롤해 보고, 접힘·펼침 도크에서 스위치 15개를 눌러 본다.
- iOS Safari 의 주소창 변화(`dvh`)와 노치 기기의 안전 영역에서 도크가 화면의 50% 를 넘지 않고, 마지막 페달이 도크에 가리지 않는지(안전 영역 높이가 페이지 아래 여백에 한 번 더 더해져 있어 노치 기기에서는 여백이 조금 넉넉하다).
- 첫 화면에서 노브가 어떻게 보이는지(390×844 에서 5개), 기본 탭이 '페달' 이라 처음 기타를 연결하려면 '입력' 탭을 한 번 눌러야 하는 흐름이 괜찮은지.
- 대표 스크린샷 6장이 실제 화면과 같은지(Chrome 헤드리스와 기기 브라우저는 글꼴·여백이 조금 다를 수 있다).
- E-04 는 기하학적 히트 테스트다(손가락 터치는 스크롤 시험에서만 CDP 로 흉내 냈다). 진짜 터치의 눌림 인식은 사람이 본다.
- E-06 의 '글자 겹침 0' 은 이 하네스의 정의(같은 카드 안에서 서로 다른 글자 상자가 가로·세로로 2 px 이상 겹침)에 따른 값이다. 1~2 px 닿는 것이나 글자와 그림(LED·풋스위치)이 눈으로 어색하게 붙는 것은 세지 않는다 — Compressor·EQ·Crunch·Fuzz 의 다시 짠 얼굴을 눈으로 본다. Figma 시안이 따로 있으면 대조한다(L-70).
- S1.8: 실제 노트북·태블릿 브라우저에서 오른쪽 패널 서랍(768~1279 px)의 열고 닫는 느낌(Esc·바깥 막 클릭·닫기 버튼), 창 크기를 끌어 1280 px 경계를 오갈 때, 실제 오디오 인터페이스를 연결한 상태 막대(두 줄로 접힌 1280~1680 px 와 한 줄인 1920 px), 카드가 340 px 를 오가며 갑자기 다른 배치로 바뀌는 모습, Tremolo 선택 상자, 키가 커진 카드(L-70·L-74), 노브 가운데를 실제 마우스·손가락으로 끌기(F-4).
- S1.8: 연결 전 첫 화면에는 페달이 하나도 보이지 않는다(1280×800 에서 첫 카드 윗선 770 px, L-76). 이 입력 패널을 접거나 옆으로 옮길지, 카드 속에서 스위치를 위로 올릴지(L-71)는 디자인 결정이라 사람이 정한다.
- S1.7: 실제 브라우저에서 사이트 데이터를 막은 상태(Safari 비공개 모드, Chrome 의 쿠키·사이트 데이터 차단)와 정말 가득 찬 저장 공간에서 알림 문구·동작이 맞는지, 오류 화면이 실제 휴대폰에서 어떻게 보이는지, 배포 사이트에서 '설정을 초기화하고 다시 시작' 흐름이 되는지(자세한 목록은 `docs/refactoring/step-reports.md` 의 S1.7).
- S2.4: 실제 브라우저에서 옛 데이터를 가진 채로 새 버전을 열었을 때 LED·노브·프리셋이 그대로인지, 실제 옛 빌드 탭이 v1 키에 쓸 때 경고가 뜨는지(e2e 는 같은 키에 값을 써서 흉내 냈다), 실제 GitHub Pages 배포에서 열려 있는 탭에 새 서비스 워커가 들어올 때 알림이 뜨는지(`dist-server` 는 배포를 흉내 낸 것이다). 이 알림이 처음 들어가는 배포 전부터 열려 있던 탭에는 알림이 없다. 자세한 것은 `docs/refactoring/step-reports.md` 의 S2.4 절.
- S2.5: 실제 기타·인터페이스로 경고 문턱과 시간(설계서 6.5 — 표의 모든 수치와 보강 2초는 초기값), 잡음 바닥이 −70~−60 dBFS 인 인터페이스에서 케이블을 뽑아도 '신호 없음' 이 안 뜨는 구간(L-122), 타건 간격이 2초보다 긴 아주 느린 연주에서 '작음' 이 늦거나 안 뜨는 것(L-119), 휴대폰 '페달'·'프리셋' 탭에서는 경고가 보이지 않는 것(L-128)과 파일 재생 중 안내가 없는 것(L-120)을 받아들일지, 실제 휴대폰에서 같은 시각에 뜨는지(가짜 마이크는 44.1 kHz·일정한 보고 간격이다).
- S2.6: **반복의 이음매 클릭**(설계서가 청취 확인으로 정했다, L-138) — WAV·MP3·AAC 파일을 반복으로 틀어 끝에서 처음으로 돌아올 때 틈이나 클릭이 거슬리는지 귀로 듣는다. 실제 휴대폰(iOS Safari·Android Chrome)에서 '음원 파일 열기' 로 파일 선택 창이 뜨는지, **손가락으로 탐색 막대를 끌 때** 막대가 재생 위치에 밀리지 않고 놓으면 다시 따라가는지(e2e 는 마우스만 본다, L-136). 입력 패널 '음원 파일' 블록의 배치(열기·닫기 버튼·반복 스위치)가 보기 좋은지, 아주 큰 파일의 열기·탐색이 답답하지 않은지. 내가 정한 동작이 맞는지: 기타를 연결하면 열어 둔 파일을 놓음(L-130), 파일이 열려 있으면 Space 가 마이크를 켜지 않음(L-131), 반복을 끈 파일이 끝나도 세션 유지(L-132), 반복 값은 저장하지 않음(L-133).
- S2.7: 실제 브라우저에서 **한글 이름의 파일**(예: '프리셋 백업.json')을 파일 선택 창으로 가져와지는지(이 환경 Chromium 은 비ASCII 경로를 시험으로 전달하지 못한다, L-147). 내려받은 파일을 열어 이름(`guitar-pedalboard-presets-YYYY-MM-DD.json`)·들여쓰기가 읽기 좋은지, 휴대폰(iOS Safari·Android Chrome)에서 내려받기·파일 선택이 되는지. 붙여넣기·충돌 대화상자의 모양(데스크톱, 휴대폰의 아래에서 올라오는 시트, 충돌 대화상자 네 버튼의 줄바꿈). 내가 정한 동작이 맞는지: 이름만 같고 내용이 다른 프리셋도 묻는 것(L-144), Esc·'가져오기 취소' = 가져오기 전체 취소(L-145), 처음 포커스 '사본으로 추가'(L-142), 0개를 가져오면 탭을 바꾸지 않는 것(L-146).
- S2.8: 되돌리기 알림의 8초가 충분한지(마우스·포커스로 멈추지 않는다, L-157), 스크린 리더가 '프리셋을 삭제했습니다' 를 읽고 키보드로 '실행 취소' 에 닿는지(L-158), 같은 이름 대화상자(붉은 테두리 덮어쓰기·새 이름 칸)와 알림이 데스크톱·휴대폰(도크와의 겹침)에서 보기 좋은지, 실제 오디오 장치로 캐비닛 IR 을 불러 둔 채 '기본 페달 설정' → '실행 취소' 했을 때 소리가 IR 적용 상태로 돌아오는지(e2e 는 화면의 IR 이름으로만 확인했다). 내가 정한 정책(L-150·L-152·L-154~L-156)이 맞는지도 사람이 본다.
- S2.9: 실제 풋스위치로 래치형(밟으면 127, 떼면 0)과 토글형(밟을 때만 신호)을 각각 학습시켰을 때 자동 지정이 맞는지(래치형을 1초 안에 밟았다 떼면 토글로 지정되는 것이 거슬리는지, L-165), Note 로 보내는 스위치도 같은지, 실제 브라우저 권한 창(Chrome 에서 권한이 '묻기' 일 때 열자마자 창이 뜨지 않고 배너 버튼을 눌러야 뜨는지·거부·차단 문구, Firefox·Safari 처럼 권한 조회가 없을 때 배너 버튼 한 번으로 연결되는지, L-163), 케이블을 뽑았다 꽂았을 때 카드가 '장치 없음' ↔ '연결됨' 으로 바뀌고 학습 없이 다시 반응하는지(휴대폰 USB OTG 포함), 배너·방식 알림의 모양과 스크린 리더 읽기. 내가 정한 정책(L-161~L-163·L-165)이 맞는지도 사람이 본다.
- S2.11: 실제 Windows·macOS 한국어 입력기에서 한글 모드로 T·A·B·Q·W·E·R·Y·`Shift + 1~6` 이 동작하는지(시험은 같은 모양의 이벤트를 보낸 것이다, L-184). 조합 중인 글자가 있을 때의 Esc. 영문(미국)·일본어·한영 겸용 배열에서 `Shift + 1~6` 과 `?`(Shift + `/`)가 같은 자리 키에서 나오는지. 도움말 문구(L-182).
- S2.12: 실제 기타·마이크에서 줄·옥타브 안내가 안정적으로 나오는지(특히 6번 줄을 낮춰 튜닝하는 중의 불안정한 소리·배음이 센 소리). 옥타브 안내 경계 ±50센트와 600센트 경계(L-188·L-189), 7현 기타·베이스, 도움말처럼 읽히는 문구('6번 줄(E2)보다 한 옥타브 높습니다'·'줄 번호를 확인하세요'·'기타/크로매틱')와 스크린 리더 낭독, 휴대폰 실기에서 전환 버튼과 긴 안내가 한 줄에 들어가는지.
- S2.13: 실제 USB 오디오 인터페이스·헤드셋·블루투스 장치를 연주 중에 뽑고 꽂았을 때 목록이 1초 안에 바뀌고 안내가 뜨는지, 같은 장치를 다시 꽂으면(연주 중이 아니면) 다시 골라지는지(브라우저·OS 마다 `devicechange` 가 오는 횟수와 시점이 다르다, L-202). Chrome·Edge 에서 실제 출력 장치로 소리가 나가는지(`setSinkId`)와 Firefox·Safari 에서 출력 메뉴가 숨고 안내가 보이는지. 실제 장치의 id 가 방문 사이에 안정적인지, 사이트 데이터를 지운 뒤 같은 장치를 이름으로 찾는지, 이름이 같은 장치가 둘일 때 어느 쪽이 골라지는지(L-196). 문구('저장된 입력 장치를 찾지 못해 기본 장치로 연결했습니다.'는 설계서 문구, '저장된 출력 장치를 쓸 수 없어 시스템 기본 출력으로 연결했습니다.'는 내가 정했다, L-197)와 스크린 리더 낭독. 저장된 출력 장치를 못 쓸 때 오류 대신 알림으로 연결되는 동작 변화(L-197)가 괜찮은지.
- GitHub Actions 에서 실제로 돌려 본 적이 없다. 처음 PR 을 올릴 때 `Install Playwright Chromium` 단계가 CI 러너에서 통과하는지 확인한다.
